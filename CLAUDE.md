# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Documentation Requirement

**Every change to this codebase must be accompanied by a documentation update.** Before closing any task:
- Update `PROJECT.md` if the change affects how the site works, admin behavior, publishing flow, card system, design, constraints, or file layout.
- Update `CLAUDE.md` if the change affects architecture, technical patterns, or AI-relevant implementation details.

Both files must stay current. Stale documentation is treated as a bug.

## Project Overview

See `PROJECT.md` for full human-readable documentation. Summary: static site for Ansar Al-Hujjah Islamic community center in Houston, TX. Hosted on GitHub Pages at ansaralhujjah.org.

## Deployment

**Dependencies (one-time):**
```bash
pip3 install markdown pyyaml
```

**Homepage changes** — no build step, push directly:
```bash
git push origin main
```

**Session note or Quran reference changes** — run build scripts first, then push:
```bash
python3 build_notes.py
python3 build_quran.py
git push origin main
```

GitHub Pages auto-deploys. No CI/CD pipeline.

## Architecture

**`index.html`** — Homepage (~1 MB due to embedded base64 flyers). All CSS and JS inline. Structure:
1. Admin-managed program cards between `<!-- AAH-ALL-CARDS-START -->` / `<!-- AAH-ALL-CARDS-END -->` markers
2. Floating social icons (`.social-float`) in the bottom-right corner — hardcoded, NOT admin-managed. WhatsApp (`#25D366`) and Instagram (gradient) circular buttons.

**`admin/index.html`** — Admin panel SPA. SHA-256 password auth in-browser.

The panel's `<style>` block carries its own token set mirroring the public scales (`--sp-*`, `--fs-*`, `--shadow-*`, `--radius-*`, `--focus-ring`). Layout: a form column plus a sticky preview/actions column above 1100px, stacked below, and sidebar-above-editor below 760px.

`updatePreview()` renders the `.program-card` composition deliberately — it is a mirror of `buildCardHtml()` / `buildPinnedCardHtml()`. **If you change the published card shape, change the preview in the same commit.** The two drifting apart is exactly what made the old `demo-card` markup (a header row plus a "Register" button) show editors something the site had long stopped publishing. GitHub token hardcoded as split string (`GH_TOKEN`) purely to dodge secret-scanning — not a real security boundary; the token should be a fine-grained PAT scoped to only this repo with Contents read/write, to limit blast radius if it leaks.

**`quran-reflections/index.html`** — Program overview page. Session list between `<!-- SESSIONS-START -->` / `<!-- SESSIONS-END -->` markers, and admin-editable description between `<!-- QURAN-DESC-START -->` / `<!-- QURAN-DESC-END -->` — both are **sibling** regions inside the `program-desc` block (not nested), each independently owned so one writer's region can never blindly overwrite the other's. `SESSIONS-START/END` is injected by `build_notes.py`; `QURAN-DESC-START/END` is injected by the admin panel.

**`quran-reflections/{slug}/index.html`** — Session article pages generated by `build_notes.py` from `.md` files in `quran-reflections/notes/`.

**`quran/verses/{surah-verse}/index.html` and `quran/surahs/{surah}/index.html`** — Quran verse and surah pages generated by `build_quran.py`.

**`build_notes.py`** — Python 3 script (requires `pip3 install markdown`). Converts Obsidian `.md` → styled HTML, resolves session/Quran wikilinks, injects session list into program index.

**`build_quran.py`** — Python 3 script (requires `pip3 install pyyaml`). Scans notes for Quran references and generates `/quran/verses/*` + `/quran/surahs/*` pages with backlinks.

**`_head.html`** — Reference-only snippet (not served). Contains shared meta/favicon/font tags for the **homepage font stack (Cinzel/Lato)**. Copy into any new homepage-style page's `<head>`. Do not use for inner pages — session, verse, and surah pages use the EB Garamond/Amiri font stack, which is defined inline inside the Python build script templates and not derived from this file.

### Comment Markers

These markers are contracts — do not remove or reformat them:

| Marker | Location | Used by |
|---|---|---|
| `<!-- AAH-ALL-CARDS-START -->` / `<!-- AAH-ALL-CARDS-END -->` | `index.html` | Admin publish + sync |
| `<!-- pinned:sisters -->` / `<!-- pinned:quran -->` | `index.html` (inside cards) | Admin sync parser |
| `<!-- admin:{cardId} -->` | `index.html` (inside cards) | Admin sync parser |
| `<!-- SESSIONS-START -->` / `<!-- SESSIONS-END -->` | `quran-reflections/index.html` | `build_notes.py` |
| `<!-- QURAN-FLYER-START -->` / `<!-- QURAN-FLYER-END -->` | `quran-reflections/index.html` | Admin publish (quran flyer sync) |
| `<!-- QURAN-DESC-START -->` / `<!-- QURAN-DESC-END -->` | `quran-reflections/index.html` | Admin publish (quran description sync) |

**Important:** `SESSIONS-START/END` and `QURAN-DESC-START/END` must remain **siblings**, never nested inside each other. They were nested for a period (via a `build_notes.py` change that reused the description area for the session index) and every admin publish that touched the description silently wiped the entire session index as a result — this broke production twice. If you ever see them nested again, un-nest them before doing anything else.

### Publishing Flow

`publishToGitHub()` in `admin/index.html` runs on every save/delete/reorder, via a shared `runPublishTransaction()` helper (also used by the undo feature — see below):

1. Get latest commit SHA on `main`
2. Get tree SHA from that commit
3. Fetch full recursive tree (`?recursive=1`) to find both `index.html` and `quran-reflections/index.html` blob SHAs
4. Fetch `index.html` blob via Git Data API (handles files >1 MB — Contents API would 422)
5. Build updated card HTML and splice it between the `AAH-ALL-CARDS-START/END` markers via `spliceMarkerRegion()`, which throws if a marker is missing or duplicated (instead of silently proceeding)
6. **Validate** the constructed HTML with `validateCardsHtml()` before any network write — re-parses it with `DOMParser`, asserts marker pairs appear exactly once, asserts the card count matches `cardOrder`, and checks flyer images aren't truncated. Throws and aborts the whole publish (no blob/tree/commit is created) if anything looks wrong.
7. If quran card has a flyer and/or description, fetch `quran-reflections/index.html`, splice `QURAN-FLYER-START/END` and/or `QURAN-DESC-START/END` (description is HTML-escaped via `esc()`), and validate with `validateQuranPageHtml()` the same way.
8. POST new blob(s) → POST new tree (with all updated files) → POST new commit → **re-fetch the branch ref and confirm it still matches the SHA fetched in step 1** (aborts with a clear error if it moved — a narrow concurrency guard) → PATCH branch ref (`force: true`)
9. On success, save the *previous* blob SHA(s) to `localStorage.aah_undo_snapshot` (24h expiry) for the undo feature, and re-fetch the live pages as a non-blocking soft check (`softValidateLivePublish()` — warns on mismatch, never blocks).

**Reading live state** (`syncFromLiveSite()`, `parseLiveSite()`, `readCardFromAnchor()`) uses `DOMParser` and real element queries, not regex — see Flyer Preservation and Sync on Login below.

**Undo:** an "Undo Last Publish" button in the topbar calls `undoLastPublish()`, which re-publishes the prior blob SHA(s) through the same `runPublishTransaction()` path (no re-upload needed — blobs are immutable and already exist). The snapshot expires after 24h since GitHub doesn't guarantee retention of blobs unreferenced by any commit.

### Card System

**Two card types:**
- **Pinned cards** (`PINNED_DEFAULTS`, keys listed in `PINNED_KEYS`): fixed keys `sisters` / `quran` / `whatsapp` / `instagram` — stored under `aah_pinned` in localStorage. Can be hidden (`removed: true`) but not deleted. `whatsapp`/`instagram` are permanent program cards (distinct from the floating `.social-float` corner icons, which still exist separately and are not admin-managed). To add another fixed card, add it to `PINNED_KEYS` and `PINNED_DEFAULTS` — every other reference to pinned cards in `admin/index.html` reads from `PINNED_KEYS`, not a hardcoded key list.
- **Event cards**: created via admin — stored under `aah_events` in localStorage with IDs like `Date.now().toString(36)` (base-36 timestamp).

Card ordering: `aah_card_order` (localStorage). Auth session: `aah_authed` (sessionStorage).

**Single markup, two layouts — `.program-card`:**

All admin-managed cards emit the same markup. The homepage `<style>` block renders it as a vertical stack below 820px and as a horizontal row (flyer left, info right) at 820px and above, where `.container` also widens from 520px to 960px. Because the breakpoint lives entirely in CSS — outside the `AAH-ALL-CARDS` markers — layout changes never require touching `buildCardHtml()`, `buildPinnedCardHtml()`, or any part of the publish pipeline. Keep it that way: express card layout changes as CSS in `index.html`, not as markup changes in the admin panel.

Flyers use `object-fit: contain` in the desktop rule. Never switch it to `cover` — flyers are text-heavy posters and cropping makes them unreadable.

The markup both layouts share:
```html
<!-- admin:{id} or pinned:{key} -->
<a class="program-card" href="{link}" target="_blank" rel="noopener">
  <div class="program-card-flyer">
    <!-- with flyer: <img src="data:{mime};base64,{b64}" alt="..."> -->
    <!-- no flyer: <svg viewBox="0 0 24 24"><path d="..."/></svg> -->
  </div>
  <div class="program-card-info">
    <div class="icon"><svg viewBox="0 0 24 24"><path d="..."/></svg></div>
    <span class="btn-text">
      <span class="btn-label">{title}</span>
      <span class="btn-sub">{subtitle}</span>  <!-- omitted if empty -->
    </span>
    <span class="arrow">→</span>
  </div>
</a>
```

`buildCardHtml(ev, idx)` and `buildPinnedCardHtml(key, pc, existingFlyer)` generate this format. `esc(str)` is the HTML-escaping utility — always use it for user-supplied strings.

**`syncFromLiveSite()` / `parseLiveSite()`** read this format via `DOMParser` and CSS selectors (`.btn-label`, `.btn-sub`, `[href]`, `.icon path[d]`), not regex — element boundaries are exact regardless of how long an embedded base64 flyer is. (An earlier regex-window implementation silently corrupted a card's title/icon to defaults once its flyer's base64 pushed the title past a fixed character window — this is why DOM parsing replaced it.)

### Flyer Preservation

When re-publishing without a new flyer, the existing base64 image is read straight off the live card's `<img>` element via `findExistingFlyer(html, markerText)` (DOM-based — replaced the old `extractFlyerAt`/`extractFlyerForPinned` regex functions). Do not remove this logic.

### Sync on Login

`syncFromLiveSite()` runs on every admin login and is **awaited** before any editing action is enabled — `showDashboard()` disables Add/Move/Delete/Restore buttons via `setSyncing(true)` until sync resolves, and keeps them disabled with a "Retry Sync" affordance if the fetch fails, rather than falling through to trusting stale local state. It fetches `../index.html` and rebuilds localStorage state (card order, event data, pinned flyers) only after a successful publish or sync (`commitLocalState()`) — not optimistically beforehand — so a failed publish can't leave localStorage diverged from the live site. Local state that was never published is lost on login from a different device.

### Obsidian Vault Dependency

Both `build_notes.py` and `build_quran.py` read verse/surah data directly from the local Obsidian vault:

```
VAULT_PATH = ~/Library/Mobile Documents/iCloud~md~obsidian/Documents/الدفتر
```

This constant is **hardcoded in both files** — if the vault moves, update it in both. The vault is only needed for rendering inline verse cards and generating `/quran/verses/*` + `/quran/surahs/*` pages. Notes without verse embeds build fine without vault access.

**Vault file format** (used by `load_verse_data()`):
- Arabic text: wrapped in `<big><big><big>…</big></big></big>` in the vault `.md` body
- Translation: body text under a level-5 heading (`#####`) — heading text = translator name
- Missing Arabic for Surah an-Nas (114) falls back to `_NAS_ARABIC_FALLBACK` dict in both scripts

### `build_notes.py` Architecture

1. Scans `quran-reflections/notes/*.md` (skips `README.md`), sorted **alphabetically by filename** — date-prefixed filenames (`YYYY-MM-DD`) are what keeps prev/next in chronological order. Renaming a file changes both its URL slug and its position in the sequence.
2. Builds `{note_title: slug}` map; slug = lowercase + collapse special chars/spaces to hyphens
3. Strips leading YAML frontmatter block (if present) before markdown rendering
4. Pre-processes each note:
   - `[[Quran S-V]]` and `![[Quran S-V]]` → inline Arabic + translation card (both forms render identically)
   - `[[N - Surah ...]]` and `![[N - Surah ...]]` → `/quran/surahs/N/`
   - `[[Note]]` and `[[Note|Display]]` → `/quran-reflections/{slug}/` only if `Note` exists in `slug_map`
   - unresolved wikilinks → plain text
5. Extracts first markdown H1 for display title
6. Runs `markdown.markdown(text, extensions=['extra', 'toc'])`
7. Wraps in article page template and injects a 3-box nav bar (`← Previous | Overview | Next →`) before the first `<hr />` in the rendered content
8. Writes to `quran-reflections/{slug}/index.html`
9. Excludes `Quran Reflections - Overview` from the homepage session list and prev/next session chain
10. Calls `inject_sessions()` to replace content between `SESSIONS-START/END` in the program index using H1 display titles
11. Session list is rendered as plain stacked links (no card-style row wrappers/arrows)
12. `[[Quran Reflections - Overview]]` wikilinks inside notes resolve to `/quran-reflections/` (hub page)

**Session page header convention:** Each note should have, immediately after the H1 title:
```markdown
**Date · Molana Farhat Abbas**

---
```
The bold line renders as a muted byline (1.05rem EB Garamond). The `---` separator triggers the 3-box nav injection — the nav is inserted between the byline paragraph and the `<hr />`.

**Overview note special handling:** `extract_overview_session_index_html()` renders the Overview note and slices its HTML from the first `<h1>` up to (but not including) the first of these H2 sections if present: `#core-framework`, `#surahs-covered`, `#central-themes`, `#key-verses`. This excerpt is embedded inline on `quran-reflections/index.html` above the session list. Structure the Overview note's H2 sections with one of those IDs to control how much is shown.

Filename governs URL; first markdown H1 governs displayed title (session list + prev/next labels).

Wikilink → URL: `[[Session 2 - Ayat 3]]` → `/quran-reflections/session-2-ayat-3/`

### `build_quran.py` Architecture

**Cross-import:** `scan_notes()` does `from build_notes import slugify`. Both scripts must be run from the repo root — running from a subdirectory will cause an import error.

1. Scans `quran-reflections/notes/*.md` (skips `README.md`)
2. Builds backlinks map from note titles/slugs to:
   - verse keys (`S-V`) from `[[Quran S-V]]` / `![[Quran S-V]]`
   - surah keys (`N`) from `[[N - Surah ...]]` / `![[N - Surah ...]]`
3. Reads verse files from Obsidian vault:
   - `Quran/Verses/Surah {S}/Quran {S}-{V}.md`
4. Reads surah files from Obsidian vault:
   - `Quran/Surahs/{N} - *.md`
5. Generates verse pages with Arabic text, translation, attribution, breadcrumbs, and backlinks
   - If Surah an-Nas source Arabic is blank in vault files, uses internal fallback text for `114:1–6`
6. Generates surah pages with metadata, referenced verses list, and backlinks

**Neither build script prunes.** A verse or surah page whose last referencing note was edited or removed stays on disk as an orphan and keeps whatever styling it had when it was generated. After a token or template change, look for pages the rebuild did not touch (`git status` shows them as unmodified) and delete the ones nothing links to.

### Icons

26 SVG Material Design icons in the `ICONS` array in `admin/index.html`. Each entry: `{ id, label, path }`. `getIconPath(id)` returns the SVG path data, falling back to the first icon if `id` is unknown.

### Design System

CSS custom properties — see `PROJECT.md` for the full token table. Key values:
- Accent mid: `rgb(148,62,12)` (warm brown)
- Background: `#d9ccbc` (beige)
- Muted text: `#6b3410` — opaque on purpose; the previous `rgba(110,55,12,0.72)` failed contrast against the beige background
- Cards: glassmorphism (`rgba(255,255,255,0.55)`) — homepage only; inner pages use plain article layout
- Scales: `--shadow-sm/md/lg`, `--sp-1`…`--sp-6`, `--fs-xs`…`--fs-2xl`, `--radius-sm/md/lg`. Use these instead of writing new one-off values.

**The token block is duplicated in four files** — `index.html`, `quran-reflections/index.html`, and the `<style>` templates inside `build_notes.py` and `build_quran.py`. Edit all four together, then re-run both build scripts. Note the brace escaping differs: `build_notes.py`'s template is an f-string so its literal braces are doubled (`:root {{ … }}`), while `build_quran.py`'s is not. `admin/index.html` has its own independent token set.
- Fonts (inner pages): EB Garamond (body), Playfair Display (headings), Alegreya SC (nav/metadata/small caps), Amiri (Arabic) via Google Fonts
- Fonts (homepage `index.html`): Cinzel/Lato — unchanged

### Verse Card Alignment

`.verse-embed-card` elements inside `<li>` items are pulled back to the article left edge via `.article li .verse-embed-card { margin-left: -24px; width: calc(100% + 24px); }` — compensates for `ul/ol { padding-left: 24px }`. This is a site-wide rule in `build_notes.py`.

For numbered lists of trials with inline verse embeds, use raw HTML with class `trials-list`:
```html
<ol class="trials-list">
<li><p>Trial description or subheading</p>
![[Quran S-V]]
</li>
</ol>
```
- `<p>` inside `<li>` renders as a Playfair Display bold subheading (1.05rem, weight 600) — the CSS uses `li > p` (direct child, not descendant) so that `<p>` elements nested inside verse cards within the same `<li>` are not styled as headings
- `![[Quran S-V]]` wikilinks inside `<li>` are processed into verse cards (lines in `<td>`/`<li>` don't start with `#`, `|`, or `>`, so `replace_verse_embeds` handles them)
- Verse cards within `.trials-list` get compact styling: 1.2rem Arabic, 0.82rem translation, reduced padding
- The general `.article li .verse-embed-card` rule already pulls cards to the article left edge

### Inner Page Layout Rule

Cards (glassmorphism boxes) are restricted to `index.html` (homepage). All inner pages use a plain article style — content flows directly on the warm beige gradient with a `border-top: 2px solid var(--accent-mid)` rule as visual anchoring. Do not introduce card wrappers on session, verse, or surah pages.

### Session Page Structure (generated HTML)

```
breadcrumb nav (Ansar Al-Hujjah › Quran Reflections › Session Title)
─────────────────────────────────────────────────────
<h1> Session Title </h1>
<p> Date · Molana Farhat Abbas </p>       ← .article h1 + p (1.05rem, muted)
[← Previous]  [Overview]  [Next →]        ← .article-header-nav (.header-nav-btn × 3)
<hr />
... session content ...
─────────────────────────────────────────────────────
session-nav (← Full Prev Title  |  Full Next Title →)  ← bottom pill nav
footer
```

The 3-box nav is generated by `render_page()` and injected via `.replace('<hr />', nav_html + '<hr />', 1)`. If no `<hr />` exists, it prepends the nav. For boundary sessions, the missing Previous or Next box renders as a `<span class="header-nav-btn disabled">` (greyed out, not a link).

### Verse Reference Display

In session notes, both `[[Quran S-V]]` and `![[Quran S-V]]` render as full inline Arabic + translation cards. The distinction is skipped for:
- Heading lines (starting with `#`)
- Table rows (starting with `|`)
- Blockquote lines (starting with `>`)

Those three contexts keep the reference as a plain link. This is enforced in `replace_verse_embeds()` via line-level prefix check and `_VERSE_EMBED_PATTERN` matching `!?[[...]]`.
